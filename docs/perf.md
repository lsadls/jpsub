# 性能优化:翻译 token 与耗时

成本单价:缓存命中 ¥0.02/M、未命中 ¥1.00/M、输出 ¥2.00/M。以下均为实测(小米 mimo-v2.6-flash)。

## 单视频实测(183 句 / 5230 字,长文)

| 配置 | 实付 prompt | completion | 耗时 |
|---|---|---|---|
| 旧版:思考开启 + 单对话 | 284 输出里 226 是思考 | 284 | 8s/句 |
| 关思考(`REASONING_EFFORT=none`) | 915 | 57 | 4.9s |
| 单对话 8 批(历史滚雪球) | 9 877(实付 7 573) | 1 196 | 58.6s |
| 8 对话并发 | 7 953(实付 5 841) | 1 175 | 15.3s |
| 并发扫描 G=2→32 | 30 420 → 谷底 14 203(G=24) → 回升 | ~3 500 | 31.6s |
| 每请求句数 gb=5→20 | 12 135 → 4 672 | ~3 800 | 14.5s |

优化后单视频 ≈¥0.011;旧版(思考+单对话)≈¥0.04。

## 机制与开关

| 机制 | 位置 | 说明 |
|---|---|---|
| 关闭模型思考 | `jpsub/.env` `REASONING_EFFORT="none"` | 输出 token 降 80%;端点不认该参数时留空 |
| 对话历史裁剪 | `HISTORY_KEEP=3` | 只留 system + 最近 3 轮,prompt 不随批数线性膨胀 |
| 动态并发 | `ai.calc_concurrency` | 按总字数线性插值(3792 字→G16,5230 字→G24),钳 8~32 |
| 每请求句数 | `group_batch=20` | 大批摊薄 system 前缀,gb≥8 后实付降 60%+;普通与长文共用 |
| 对照表预替换 | `ai._glossary_sub` + `prompts/bb.txt` | 词条不进 system,发送前把原文词条替换成 `⟦译文⟧`;实测成功率 50% vs 裸发 12.5% |
| 拒译降级 | 长文 `refuse_fix=False` | 缺行不补问(补问轮整段重发历史),标 `[[原句]]` 留给续翻 |
| 批失败二分 | `ai.translate_texts_parallel._flush` | 整批被拒后对半拆重试,拒译请求不计费,越拆越便宜 |
| 毒句预筛单发 | `_run_group` | 命中 glossary 词条的句子先单发,不连累整批 |
| 失败句落盘 | 工作目录 `translate-fails.txt` | 一句一行,提取关键词加进 glossary.txt |
| OCR 计数 | `ocr.REQUESTS` | OCR 结束打印 `OCR 消耗 N 次请求(百度月额度 3500 次/月)`,只计成功计费请求 |
| token 汇报 | `ai._USAGE` | 翻译结束打印 `token 消耗: 命中X 未命中Y 输出Z ≈¥N` |

## 规律备忘

- 并发过低(单对话/2):组内历史滚雪球,prompt 暴涨;过高(≥32):system ×G + 补问轮增多,回升
- 拒译的请求不计输出费:降级策略(不补问/二分)几乎零成本
- 缓存命中由服务商按前缀判定,system 开头稳定 + 历史裁剪不破坏前缀
- 调优工具:`abtest_glossary.py`(对照表 A/B 成功率);重测并发用不同 `concurrency`/`group_batch` 跑 `jpsub text` 对比末尾的 token 汇报
